# Agent Instructions — react-native-mlkit-translation

Published npm library: on-device text translation with Google ML Kit for React Native, New Architecture only (TurboModule generated by Codegen; React Native 0.76+). Kotlin on Android, Objective-C++ on iOS. The JS layer validates input, queues translations FIFO through one native translator, deduplicates model downloads per language, and keeps a model state store with a React hook. Hand-written types, no Expo config plugin. Jest, ESLint, and TypeScript checks are installed as devDependencies; Kotlin unit tests and native builds run through the fixtures in `example/`. The main consumer is the Jupi app (`en ↔ vi`).

## Working conventions

- Follow the existing structure: plain JS in `src/` shipped untranspiled (`index.js` public API, `translation-queue.js`, `model-store.js` with `ModelStatus`, `translation-error.js` with `TranslationErrorCode`, `languages.js` with `TranslateLanguage`), types in `src/index.d.ts`, Kotlin in `android/src/main/java/com/reactnativemlkittranslation/`, Objective-C++ in `ios/`, CocoaPods spec `RNMLKitTranslation.podspec`. Read the implementation before assuming behavior.
- Tests: JS tests in `__tests__/` (mocked `react-native`, deferred Promises instead of timers), consumer type checks in `type-tests/`, Codegen spec check via `tsconfig.codegen-spec.json`, Kotlin tests in `android/src/test/`. Translator ownership logic lives in `TranslatorSlot.kt`; model-check budgeting lives in `ModelAvailabilityCheck.kt`. Both avoid Android/ML Kit APIs and run in JVM tests.
- Architecture: `src/NativeMLKitTranslation.ts` is the Codegen spec (`codegenConfig` in `package.json`, library `RNMLKitTranslationSpec`). Android extends the generated `NativeMLKitTranslationSpec`; iOS conforms to the generated protocol and returns `NativeMLKitTranslationSpecJSI`. No Legacy Architecture code.
- Native invariants: at most one translator alive; translator work serialized on one thread/queue; `translate` never downloads; download success/failure never creates a translator; after `invalidate` no promise of the old instance settles. The JS queue owns ordering; native rejects a concurrent call instead of queueing it. Android model-presence checks before translate/prepare share a 10-second monotonic budget; timeout rejects `MODEL_MANAGER_FAILED` before translator acquisition. Queue wait, warm-up, and translation are outside this budget.
- Never log, persist, or send translated text (input or output) from library code, example logs included.
- Example: the committed fixtures `example/rn-0.88/` (React Native CLI) and `example/expo-sdk-58/` (Expo, `android/` and `ios/` generated by `npx expo prebuild` and git-ignored) render `example/shared/TranslationScreen.js`, which runs the self-test in `example/shared/selfTest.js` on launch. Other versions are generated on demand with `example/scripts/create-fixture.sh <version>` into git-ignored `example/generated-rn-<version>/`. `example/scripts/install-library-into-fixtures.sh` packs the library and installs the tarball; see `example/README.md`.
- `.npmrc` sets `legacy-peer-deps=true` so `npm install` does not pull `react-native` as a peer dependency.
- Enum constants: every fixed set of string values in the public API (languages, error codes, model statuses, and any future option or result values) is exported as a frozen constant object with UPPER_SNAKE_CASE keys, declared in `src/index.d.ts` as a `const` with literal values plus a type of the same name (`TranslateLanguage`, `TranslationErrorCode`, `ModelStatus`). The API keeps accepting the plain strings. Library code, docs, and examples use the constants, never bare string literals (tests may use the plain strings where they check the values sent to or received from native code); a new value is added to the constant, the type, `docs/api-reference.md`, and `type-tests/` together. Do not use TypeScript `enum`.
- Keep the language list, error codes, the native module name `MLKitTranslation`, the Kotlin package, and the Codegen library name consistent across JS, types, Kotlin, Objective-C++, Gradle, podspec, and `react-native.config.js`.
- Every public export has a type declaration, a place in the grouped README API table, and a section in `docs/api-reference.md`. README stays short: only what a user needs to integrate right away (one-line pitch, a few features, a Requirements table before installation so the iOS and Android minimums stand out, installation steps per platform, one minimal usage example, a grouped API table, links to `docs/`). Every other explanation, extra example, option, or limit lives in `docs/` and is linked from README. Keep JSDoc, types, README, and `docs/` aligned with behavior in the same task. State what was actually checked rather than marking written code as verified.
- Treat the public API as shared with unknown consumers. Before changing existing behavior, follow `public-api-change-safety`; present semver impact and ask when consumer-visible behavior changes or remains uncertain. Prior approval for that same impact remains valid.
- Do not add runtime dependencies, dev tooling, new native SDKs, or committed example fixtures without user approval. Changing the pinned ML Kit versions (`com.google.mlkit:translate`, `GoogleMLKit/Translate`) is a public change. Search for an existing equivalent before adding a helper or constant.
- Approved plans live in `docs/superpowers/plans/` (local only, git-ignored). A plan's decisions and execution limits are user approval for its tasks; read it before working on one. When a task changes structure, tooling, or scripts, update this file and the affected skills in the same task.
- A finishing pass runs only when requested. Routine targeted verification is still required. Never claim checks passed without running them.
- Preserve the user's preexisting changes. Commit, push, tag, version bump, and `npm publish` require user instruction.

## Execution authorization

Checks that need no install may run freely: `node --check` on JS files, `bash -n` on scripts, `npm pack --dry-run --ignore-scripts`, `git diff --check`, and the installed scripts `npm test -- --runInBand`, `npm run lint`, `npm run typecheck` (none of them build or launch an app).

Do not install dependencies, download tools via `npx`, generate a fixture, run `pod install`, compile Kotlin or Objective-C++, run Kotlin/Gradle tests or `xcodebuild`, start Metro, or build/install on a device or simulator solely to verify an edit. These need user authorization; reuse authorization already given in the session. For device verification, ask which host app, platform, and device/OS version to use. Stop background processes you started when done unless the user asked to keep them running; report any remaining process.

## Native CI

`native-fixtures.yml` automatically builds RN and Expo fixtures on Android/iOS for PRs and pushes to `main` touching source, native code, fixtures, package/lockfile, autolinking, podspec, `.npmrc`, or the workflow. Kotlin tests run once through RN using repository sources. Manual dispatch retains selected/generated fixtures. Automatic runs supersede earlier runs on the same event/ref; manual runs stay independent. This CI configuration does not authorize local native builds or device actions.

## Release

Only on user instruction: choose the semver bump from the public API impact, update `version` in `package.json` and the `CHANGELOG.md` heading, run `npm pack --dry-run --ignore-scripts` to confirm the tarball contents, and merge to `main`. Publishing is done by `.github/workflows/release.yml` when the tag `v<version>` is pushed for a commit on `main`; it re-runs the checks, verifies the tag matches `package.json`, and publishes with provenance (`latest`, or `next` for prerelease versions) through npm Trusted Publishing (no token stored). The podspec reads its version from `package.json` and its source tag is `v<version>`. Pushing the tag is the publish step: it needs the same explicit user instruction. Never tag a dirty tree or without stating the exact version.
